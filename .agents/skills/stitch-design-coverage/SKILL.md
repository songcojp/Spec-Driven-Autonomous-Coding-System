# Stitch Design Coverage

## Workflow

1. Confirm the Feature ID, workspace root, and `deliveryHarnessRef` path from the Feature's `spec-state.json`.
2. Read the `docs/agentic-spec/ui/coverage/design-consumption.md` (or the path in `deliveryHarnessRef.path`) to obtain all `DHI-###` design target rows.
3. For each `DHI-###` row, call Stitch MCP to generate a WYSIWYG screen.
4. Collect the returned Stitch screen IDs.
5. Write the screen IDs to `spec-state.json` and advance `harnessStatus`.
6. Return the runtime-supplied structured output shape exactly.

## Guidance

This skill is the **only authority** that may advance `deliveryHarnessRef.harnessStatus` to `"ready"`. No other skill or manual step may do so.

### DHI Row Processing

For each `DHI-###` row in `design-consumption.md`:

- Extract: `id`, `tool`, `title`, `viewport`, `layoutHierarchy`, `representativeData`, `interactionStates`, `designSystemConstraints`, `toolReadyPrompt`.
- Skip rows where `tool != "stitch"` or `status = "blocked"` (record skipped IDs in gaps list).
- Call `mcp_stitch_generate_screen_from_text` with the `toolReadyPrompt` and `designSystem` from the traceability ledger.
- On success: record the returned screen ID in a `dhiToScreenId` map.
- On failure: add the DHI ID to the `blockedDhiIds` list with reason.

### Writing to spec-state.json

After processing all DHI rows, patch the Feature's `spec-state.json`:

```json
"deliveryHarnessRef": {
  "path": "<same as before>",
  "workflowRefs": ["<same as before>"],
  "dhiRefs": ["<same as before>"],
  "tmRefs": ["<same as before>"],
  "stitchScreenIds": ["<screen_id_1>", "<screen_id_2>"],
  "harnessStatus": "<status>"
}
```

Status resolution rules:

| Condition | `harnessStatus` |
|---|---|
| All DHI rows processed successfully, `stitchScreenIds` non-empty | `"ready"` |
| Some DHI rows processed, some blocked (partial coverage) | `"gap"` |
| Stitch MCP unavailable (connection error, auth error) | `"blocked"` |
| No DHI rows found in the coverage document | `"blocked"` |
| All DHI rows were already skipped (`blocked` status) | `"gap"` |

**Never set `harnessStatus: "ready"` when `stitchScreenIds` is empty.**

### Blocked Handling

If Stitch MCP is unavailable:

1. Do **not** invent screen IDs or fake the `harnessStatus`.
2. Set `harnessStatus: "blocked"` with `blockedReasons` explaining the failure.
3. Add a `ProtocolGap` of category `design_gap` and severity `P1` to the Feature's gap list.
4. Return skill output status `"review_needed"` with `reason: "stitch_mcp_unavailable"` and a `nextAction` recommending manual retry or alternative design tool.
5. The Feature will remain unschedulable by the scheduler until a successful `stitch-design-coverage` run advances `harnessStatus` to `"ready"`.

### Coverage Verification

After all DHI rows are processed, produce or update `docs/agentic-spec/ui/coverage/stitch-coverage-report.md`:

- Table of `DHI-###` → Stitch Screen ID mappings (or `blocked` with reason)
- Summary: total DHI rows, successful, blocked, skipped
- `harnessStatus` value and effective date
- Link to traceability ledger for downstream Feature scheduling

## Product Usability Autonomy Wrapper

Apply FEAT-024 Product Usability Autonomy when this skill affects P0/P1 design targets:

- Record each Stitch screen generation as a `DecisionLog` entry (`auto_decided` or `blocked_open_question`).
- Record DHI rows that cannot be processed as `ProtocolGap` with category `design_gap`.
- Preserve or produce `UsabilityEvidence` linking each generated Stitch screen to the `UH-###` user scenarios from `agent-user-harness.md`.

- Read `references/specdrive-output.md` when invoked by an adapter that requires structured execution output.

## Boundaries

- Do not generate placeholder or draft screens and mark them as `ready`. Only WYSIWYG screens generated by Stitch MCP count.
- Do not modify `DHI-###` or `TM-###` source rows in `design-consumption.md` or `acceptance-automation.md`; only update `stitch-coverage-report.md` and `spec-state.json`.
- Do not call Stitch MCP for non-DHI artifacts (e.g., concept images, documentation screenshots). Route those to `design-ui-spec`.
- If `deliveryHarnessRef` is missing from `spec-state.json`, run `design-ui-spec` first to create the PDC and set `harnessStatus: "pending"`.
